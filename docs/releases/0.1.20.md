# 0.1.20 — Concurrent helper setup

Boot and app-start setup calls now share the existing setup lock with a bounded
30-second wait. After acquiring it, each call validates the installed bundle and
rereads the installation record. An already verified current worker is reused;
an upgrade stops/replaces the previous generation once. Bundle verification and
the narrowly scoped installation-directory repair are inside this lock too.

A wait that exceeds the bound reports that setup is still in progress. It is not
cached as a permanent app-session failure; reopening a helper-backed menu can
check again. An uncertain RPC timeout, ownership or integrity rejection, and a
worker lock held without a verified reusable worker still remain failures. No
lock is deleted and no arbitrary process is signalled.

Setup logs can now include `setup_waiting`, `setup_resumed` and `worker_reused`,
followed by the usual `setup_ready`. Entries include a PID and startup entries
identify the command, so overlapping invocations can be distinguished.
Saved settings, restoration records and all
0.1.19 wave settings/rendering are retained.

The regression tests use independent processes and real filesystem locks with
inert native operations. They cover concurrent clean installs/upgrades, one
worker launch, preserved configuration, failed-owner recovery and bounded waits.
They do not simulate a TV package-manager update or prove native feature support.

Keep this as a test build pending on-TV upgrade validation. The previous full
browser run's Background activity read-count failure has not been addressed by
this change. Existing native model-gating and worker-output limitations remain.
